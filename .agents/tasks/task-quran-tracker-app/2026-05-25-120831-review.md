# Offline Quran Progress Tracker Desktop Application

A greenfield Electron desktop app for tracking Quran memorization progress, built around a SQLite-backed service layer with an Arabic-first RTL renderer. The architecture cleanly separates main-process services from the renderer via context-isolated IPC, with a consistent pattern across all domain areas: students, levels, surahs, progress tracking, reports, export/import, and backup. Watch for: SQL injection surface in dynamic query construction (confirmed), lack of input validation on IPC boundaries (confirmed), restore-while-running database corruption risk (confirmed), and incomplete test coverage of renderer logic and error paths.

## High-level view

The Electron architecture follows security best practices for context isolation and disabled node integration, but the IPC boundary does no input validation — any renderer-side bug or future XSS in dynamically-inserted HTML would have unrestricted access to all database operations. The CSP in the HTML is well-configured (no `unsafe-eval`, `script-src 'self'`), which mitigates the XSS vector significantly.

The service layer is well-structured and consistent. Each service receives `db` as a parameter, making them testable in isolation with in-memory SQLite. The progress matrix is the most complex piece — it builds an in-memory map from two IN-clause queries whose parameters are constructed from application-trusted IDs, but the pattern of interpolating placeholders dynamically warrants attention for maintainability.

The import system supports merge and replace modes with reasonable conflict tracking, but replace mode does destructive DELETEs without creating a pre-operation backup point, leaving no recovery path if the imported data is malformed mid-transaction.

The backup/restore mechanism copies the `.db` file at the filesystem level while the database connection is still open and potentially mid-write. SQLite WAL mode means the `.db` file alone may not capture pending WAL data, producing a potentially corrupt backup.

The renderer is vanilla JS with a global router pattern. HTML is constructed via string interpolation with user-provided Arabic text (student names, notes) that is never escaped, creating a DOM injection path from stored data.

## Issues (7)

<details>
<summary>Issues (7)</summary>

1. **Stored XSS via unescaped user input in HTML templates** — Student names, notes, and other user-provided text are interpolated directly into innerHTML without HTML escaping. Sanitize all user-derived text before insertion (e.g., replace `<`, `>`, `&`, `"` characters).
2. **No IPC input validation** — The main process IPC handlers pass renderer-provided arguments directly to service functions without type checks, length limits, or schema validation. Add validation at the IPC boundary.
3. **Dynamic SQL placeholder construction** — `getProgressMatrix` builds `IN (?)` clauses by mapping array lengths. While the values are parameterized, the pattern is fragile; a future change could introduce injection. Consider using a fixed helper or `json_each` approach.
4. **Replace-mode import lacks transactional safety** — `importFromExcel` and `importFromBundle` in replace mode delete all existing data then insert new data, but the operations are not wrapped in a single transaction. A failure mid-import leaves the database empty.
5. **Backup copies live database file without using SQLite backup API** — `fs.copyFileSync` on an open WAL-mode database can produce a corrupt copy. Use `better-sqlite3`'s `.backup()` method or `VACUUM INTO` instead.
6. **Restore overwrites database while connection is open** — The restore handler copies a backup file over the live database path, but `main.js` holds an open `db` handle to that same file. The existing connection will operate on stale state or corrupt data. Restart the app or reopen the connection after restore.
7. **Student profile hardcodes 114 surahs instead of respecting level** — `StudentProfileScreen._calculateStatusCounts` always divides by 114 surahs regardless of the student's assigned level, making progress percentages incorrect for level-scoped students.

## Stored XSS via innerHTML interpolation

Every renderer screen constructs HTML via template literals and inserts user data directly:

```javascript
// students.js
html += `<strong>${student.name_ar}</strong>`;
// student-profile.js
`<div class="note-content">${note.content}</div>`
// progress-matrix.js
html += `<span class="progress-cell-label">${label}</span>`;
```

Since the data originates from user-entered Arabic text stored in SQLite, an attacker (or even a teacher accidentally pasting HTML) can inject arbitrary markup. The CSP blocks inline scripts (`script-src 'self'`), which prevents classic `<script>` injection — this significantly limits the exploit severity. However, injected HTML can still deface the UI, create misleading content, or inject event handlers via `onerror`/`onload` on elements like `<img>`.

**Confidence: confirmed.** The code paths are visible and no escaping utility exists anywhere in the codebase.

**Recommendation:** Create a small `escapeHtml` utility and apply it to all user-derived values before interpolation into templates. Alternatively, use `textContent` assignment for simple text nodes.

## No input validation at the IPC boundary

The main process IPC handlers trust renderer-supplied arguments completely:

```javascript
ipcMain.handle('addStudent', (event, student) => {
  return studentsService.addStudent(db, student);
});
ipcMain.handle('updateProgress', (event, progress) => {
  return progressService.updateProgress(db, progress.student_id, progress.surah_id, { status: progress.status });
});
```

If `student` is `null`, or `progress.student_id` is a string, the services will either throw unhandled exceptions or produce unexpected database behavior. The `updateProgress` service validates status values (good), but no other service validates types or required fields at the IPC boundary.

**Confidence: confirmed.** The preload exposes raw `ipcRenderer.invoke` pass-throughs and the main handlers destructure without validation.

**Recommendation:** Add a validation layer (even just type assertions) in the IPC handlers before calling services. This also protects against future renderer bugs.

## Dynamic SQL placeholder interpolation

The `getProgressMatrix` function builds SQL with dynamically-constructed placeholder lists:

```javascript
progress = db.prepare(`
  SELECT student_id, surah_id, status, last_reviewed
  FROM progress
  WHERE student_id IN (${studentIds.map(() => '?').join(',')})
    AND surah_id IN (${surahIds.map(() => '?').join(',')})
`).all(...studentIds, ...surahIds);
```

The values are parameterized (safe), but the query string is rebuilt on every call with a variable number of placeholders. This is a common pattern in SQLite applications, but it scales poorly (SQLite has a default variable limit of 999) and makes the code harder to audit. With 50 students and 114 surahs, the parameter count reaches 164 — well within limits, but if the app grows to hundreds of students without a level filter, it could hit the ceiling.

**Confidence: confirmed.** The code is visible. The injection risk is mitigated by parameterization, but the scaling concern is real for unfiltered queries.

## Replace-mode import lacks transactional wrapping

In `importFromExcel` with `mode === 'replace'`:

```javascript
if (mode === 'replace') {
  db.prepare('DELETE FROM student_notes').run();
  db.prepare('DELETE FROM progress').run();
  db.prepare('DELETE FROM students').run();
  db.prepare('DELETE FROM level_surahs').run();
  db.prepare('DELETE FROM levels').run();
}
// ... then import from Excel rows individually
```

These operations are not wrapped in a transaction. If the Excel reading succeeds but insertion fails partway (malformed data, constraint violation), the database is left in a partially-empty state with no recovery path. The bundle import has the same issue.

The seed operation correctly uses `db.transaction()` — this same pattern should wrap replace-mode imports.

**Confidence: confirmed.** The code shows no transaction wrapper around the replace + re-import sequence.

## Backup copies live WAL-mode database via filesystem

```javascript
// backup.js
fs.copyFileSync(dbPath, backupPath);
```

The database is opened with `journal_mode = WAL`. In WAL mode, uncommitted data lives in a separate `-wal` file. Copying only the `.db` file via `fs.copyFileSync` while the database is open can produce a backup that is missing recent writes or is internally inconsistent. The `better-sqlite3` library provides a `.backup()` method that uses SQLite's online backup API, which produces a consistent snapshot regardless of WAL state.

The auto-backup on `before-quit` is particularly risky because it fires during shutdown when writes may still be in flight.

**Confidence: confirmed.** `database.js` sets `journal_mode = WAL`, and `backup.js` uses `fs.copyFileSync`.

## Restore overwrites database under an open connection

```javascript
// backup.js
function restoreBackup(backupPath, dbPath) {
  fs.copyFileSync(backupPath, dbPath);
  return { success: true, restoredFrom: backupPath };
}
```

The `main.js` `db` variable holds the `better-sqlite3` connection open for the lifetime of the app. When `restoreBackup` copies a different `.db` file over the same path, the open connection's file descriptor still points to the old file (on most OSes, the old inode). On Windows, this would fail entirely because the file is locked. On macOS/Linux, the app would continue operating on the deleted old file while the new backup sits at the path — meaning the restore has no effect until the app is restarted, and new writes go to the unlinked old file.

**Confidence: confirmed.** The `db` handle is never closed or reopened after restore.

**Recommendation:** Close the database, copy the backup, reopen the database, and reload the current screen. Or prompt the user to restart the app.

## Student profile progress calculation ignores level scope

In `student-profile.js`:

```javascript
_calculateStatusCounts() {
  // ...
  counts.NOT_STARTED = Math.max(0, 114 - totalTracked);
  return counts;
}

_calculateProgress(counts) {
  const memorized = (counts.MEMORIZED || 0) + (counts.PERFECT || 0);
  return Math.round((memorized / 114) * 100);
}
```

This always uses 114 as the total, regardless of whether the student is assigned to a level with only 16 surahs (Level 1). The progress service's `getStudentProgress` and `getProgressStats` correctly scope by level, but the renderer-side profile screen ignores this and fetches raw progress via `window.api.getProgress(studentId)` (which returns all progress rows without level context), then divides by 114.

A student in Level 1 who has memorized all 16 assigned surahs would show 14% progress instead of 100%.

**Confidence: confirmed.** The renderer code is visible and the service APIs it calls are documented above.

## Test coverage gaps

The 115 tests cover the service layer well: schema creation, seeding, CRUD for students/levels, progress tracking, import/export, and backup. Notable gaps:

- **Not tested:** Renderer screens, router, modal component, and all UI interaction logic. Since these are vanilla JS without a framework, they require a DOM environment (jsdom or similar) which isn't configured.
- **Not tested:** Reports service (`getClassReport`, `getWeakReport`, `getReviewNeededReport`, `getGlobalSummary`). These contain non-trivial SQL joins and aggregations.
- **Not tested:** PDF export (hard to test, but at minimum the data assembly could be tested separately from PDF rendering).
- **Not tested:** Error paths in IPC handlers (what happens when services throw).
- **Not tested:** The `surahs` service and `notes` service have no dedicated test files.

**Confidence: confirmed.** The test file listing and Jest output show exactly which services have coverage.
