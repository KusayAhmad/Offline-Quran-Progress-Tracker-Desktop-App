# Settings persistence, report filtering, and import template support

This change fixes a language persistence bug (settings were hardcoded to Arabic), adds level-filtered reports with progress calculation transparency, introduces an import template download feature with documentation, and addresses a dropdown visibility issue in the progress matrix. The implementation touches the full Electron stack: schema (new `settings` table), services, IPC handlers, preload bridge, and renderer screens with associated CSS.

**Watch for:** Missing CSS for the reports filter bar controls (`reports-filter-bar`, `filter-select` have no styles) — confirmed. Race condition between `applyStoredLanguage()` and the initial `navigate('dashboard')` call since both are async but fire independently — likely. The `source_id` in export bundles uses a weak hash that can trivially collide — confirmed.

## High-level view

The language bug was caused by the settings service always returning `'ar'` without reading from any persistence layer. The fix introduces a `settings` key-value table with upsert semantics and splits storage: language goes to `settings`, profile fields stay in `profiles`.

Reports gained a level filter dropdown and a new "Level Summary" tab. When filtered by level, progress percentages are recalculated against only that level's surahs rather than all 114, and the UI explains the calculation basis. The service layer duplicates significant logic from `getClassReport` in `getClassReportFiltered` rather than having one call the other.

The import template feature generates a three-sheet Excel file matching the expected import format. The import/export screen now documents the file structure and merge/replace semantics.

The progress matrix dropdown now detects viewport overflow and flips upward via a CSS class toggled from JS. The legend received sticky positioning and the matrix content area gained minimum height constraints to prevent the single-student clipping problem.

The reports filter bar HTML is rendered without corresponding CSS rules for `.reports-filter-bar` and `.filter-select`, so the dropdown will render unstyled.

<summary>Issues (6)</summary>

1. **Missing filter bar CSS** — `.reports-filter-bar` and `.filter-select` have no CSS rules in any stylesheet. Add styles to `reports.css` so the filter dropdown renders with proper layout and appearance.
2. **Init race in language application** — `applyStoredLanguage()` is async but `navigate('dashboard')` fires immediately after it without awaiting. If the settings IPC resolves after the first render, the direction correction flickers. Await `applyStoredLanguage()` before the first navigate, or guard `renderScreen` with a "settings loaded" flag.
3. **Weak source_id hash** — The export bundle `source_id` uses a hand-rolled DJB-like hash over teacher name + institution + timestamp. Different teachers exporting at the same instant could collide, and the timestamp guarantees uniqueness only per millisecond. Use `crypto.randomUUID()` (available in Node 19+) or at minimum `crypto.randomBytes(8).toString('hex')`.
4. **Duplicated report logic** — `getClassReportFiltered` duplicates ~50 lines from `getClassReport`. Factor the shared student-summary-building into a helper to reduce divergence risk when the progress schema changes.
5. **Level summary N+1 queries** — The renderer calls `getLevelReport` in a loop for every level. Each call issues multiple SQL queries. For a halqa with many levels this will be perceptibly slow. Consider a batch endpoint.
6. **`escapeHtml` not applied to error messages** — `showResult()` in import-export.js injects `result.message` directly via `innerHTML` without escaping. If an import error message contains user-controlled data (e.g. a filename with angle brackets), it becomes an XSS vector.

## Init race in language application

`applyStoredLanguage()` in `app.js` is called from `init()` but is not awaited:

```javascript
init() {
  // ...
  this.applyStoredLanguage(); // async, not awaited
  this.navigate('dashboard'); // also async, fires immediately
}
```

If the IPC round-trip for `getSettings` takes longer than the dashboard render, the page briefly shows the wrong direction before correcting. On a local SQLite DB this is unlikely to be perceptible, but a future network-backed settings store would surface it immediately. The fix is straightforward: `await this.applyStoredLanguage()` before navigating (requires making `init()` async, which is fine since it's called from a DOMContentLoaded handler).

## Report filtering and N+1 queries

`getClassReportFiltered(db, filters)` branches on `filters.level_id`. When a level is specified, it joins `progress` through `level_surahs` to scope the denominator. The unfiltered path duplicates the logic of `getClassReport` almost verbatim — the two functions will drift apart if one gets a bug fix the other doesn't.

The Level Summary tab loops over all levels and calls `getLevelReport` for each:

```javascript
for (const level of levels) {
  const report = await window.api.getLevelReport(level.id);
  if (report) levelReports.push(report);
}
```

Each `getLevelReport` call runs 3-4 SQL queries (level lookup, students, surahs, progress per student). For a halqa with 5-10 levels this is acceptable; beyond that the serial await chain will noticeably block the UI.

## Import template sample data risk

`generateImportTemplate(filepath)` creates a three-sheet workbook with headers and one example row per sheet. The example data uses real-looking Arabic names and status values (`MEMORIZED`), which means a user could import the template as-is and get a phantom student. A comment row or distinguishing placeholder (like "--- DELETE THIS ROW ---") would reduce surprise imports.

## Dropdown viewport detection

The dropdown flips upward when `rect.bottom > viewportHeight`:

```css
.progress-cell-dropdown.open-upward {
  bottom: 100%;
  top: auto;
  margin-bottom: 4px;
  margin-top: 0;
}
```

Horizontal overflow in RTL isn't checked. If the dropdown's `min-width: 160px` exceeds available horizontal space in a narrow viewport, it would clip. This is unlikely given typical matrix cell widths but is an unhandled edge case.

## Missing CSS for reports filter bar

The reports screen renders:

```html
<div class="reports-filter-bar" id="reports-filter-bar">
  <select id="report-level-filter" class="filter-select">...</select>
</div>
```

Neither `.reports-filter-bar` nor `.filter-select` appear in any stylesheet. The select will render with browser defaults and no spacing relative to the tabs below it.

## Export bundle source_id weakness

```javascript
const sourceStr = teacherName + institution + exportDate;
let sourceHash = 0;
for (let i = 0; i < sourceStr.length; i++) {
  const ch = sourceStr.charCodeAt(i);
  sourceHash = ((sourceHash << 5) - sourceHash) + ch;
  sourceHash = sourceHash & sourceHash;
}
const sourceId = Math.abs(sourceHash).toString(36);
```

This is a 32-bit hash converted to base-36. The feature is described as supporting "merge conflict detection" between multiple teachers. If two teachers with similar names at the same institution export within the same millisecond, the hash collides. A UUID or random hex string would be more appropriate for an identifier meant to be globally unique.

## XSS in import-export result display

`showResult` in import-export.js uses:

```javascript
container.innerHTML = `<p>${result.message || 'error'}</p>`;
```

If `result.message` contains user-controlled content (e.g., a filename like `<img src=x onerror=alert(1)>.xlsx`), this becomes an injection point. The Electron context reduces severity (no cross-origin attack surface), but it can still execute arbitrary JS in the renderer process. The `escapeHtml` utility is available and used elsewhere in the same file.
